# Upgrade to devrouter 0.6.1

This patch repairs managed-state persistence and explicit stop recovery after
container replacement. It also makes interrupted or stalled ensure operations
inspectable without waiting for the lifecycle mutation lock. Repository schemas
and existing routing configuration remain compatible.

## Task

Install the published 0.6.1 CLI and inspect `devrouter upgrade 0.6.1`. Within an
authorized consumer adaptation, bump `devrouter.version` in `.devrouter.yml`
and refresh existing generated agent guidance with `devrouter repo agents`.
No schema migration, application restart or consumer data reset is required by
the metadata upgrade itself.

Inspect a managed operation with `devrouter status --repo <exact-checkout>
--json`. For explicit diagnostic output, use `devrouter logs --repo
<exact-checkout> --tail 100`. The ensure output snapshot is private and bounded
to 32 KiB, has no follow mode, and is unavailable when its operation evidence
cannot be validated. Stage and output freshness do not prove liveness. Worker
handshake and cancellation limits are distinct from execution, which has no
implicit deadline.

Ordinary stop continues to refuse changed immutable ownership. For a separately
authorized recovery of replaced containers, use `devrouter stop <exact-checkout>
--repair --json`. This requires complete provider, daemon, source, configuration,
mount, population and exact-ID proof, preserves volumes and cannot combine with
`--delete`. A service network namespace is equivalent only when live inspection
proves the exact owned target; changed or uncertain evidence still refuses.
`ensure --repair` remains a separate recovery operation. Do not bypass a
refusal with raw Docker or provider mutations.

## Validation

1. Confirm the installed CLI and executable with `devrouter -V`, and inspect
   this adaptation prompt. Run existing static consumer checks for actual edits.
2. When runtime verification is separately authorized, use the exact checkout
   for ordinary ensure, actual application work and supported recovery. Check
   data retention and neighbour isolation rather than treating readiness as
   proof of working application behavior.
3. After the last runtime check, stop that exact checkout and verify its provider
   is stopped and its owned routes are absent unless explicitly kept running.
   An unknown worker, ownership conflict or surviving resource remains a refusal.

## Report

Report installed version and executable, consumer metadata changes, checks and
producing source/package identities, any explicit recovery performed, retained
data proof, and final provider/route state. Distinguish publication, global
installation and consumer runtime acceptance. Keep private runtime data out of
shared source and release artifacts.
