# Upgrade to devrouter 0.1.0

This release is the first stable cut of the reliability program. The managed
lifecycle is now driven by durable intent instead of a live CLI process, capacity
admission refuses instead of guessing when its evidence is incomplete, and the
agent harness gate serves Claude Code and the Codex CLI in the shape each of them
accepts.

## What changed for a consumer

- A managed `stop` whose physical cessation is proven against a positively
  absent capacity ledger now completes instead of staying in `stopping`
  forever. An intact ledger keeps today's settlement and revision fencing, and
  every other ledger classification still refuses.
- `devrouter capacity reconcile --yes [--json]` is the explicit forward
  recovery for a provably absent ledger. It refuses without `--yes`, while any
  journal binding remains, and when a declared runtime domain cannot be observed.
- `devrouter doctor` reports `global.cli-path` when another `devrouter` on
  PATH is newer than the running CLI or when the shell resolves a different
  install. Keep one install authoritative before trusting lifecycle state.
- `devrouter harness gate` defers one agent tool call while the checkout's
  durable phase is `queued`, `starting`, `verifying`, `recovering` or
  `stopping`, waits inside the hook process with no model turns, and refuses
  once with recovery guidance when the budget runs out. It identifies the
  requesting harness from its payload: Claude Code receives
  `permissionDecision: allow`, the Codex CLI receives the same guidance as
  `additionalContext` because it reports an `allow` decision as unsupported
  hook output. A re-delivered call returns one refusal that names the earlier
  decision instead of repeating a command that may already have run.
- A fixed host-port conflict whose holder is the shared `devrouter-traefik`
  router names the consumer's own published binding as the side to change instead
  of telling the agent to stop the router.
- Managed `ensure` accepts a devnet upstream served by any Compose project owned
  by the exact worktree, while a container owned by a different worktree or by a
  shared project outside the checkout is still refused.

## Task

Use the published 0.1.0 CLI. Update the repository `devrouter.version` metadata
only when consumer source changes are authorized, and refresh generated agent
guidance only with its owner's authority. No schema, command, flag, environment
or journal migration is needed, and the upgrade rewrites no runtime state.

Two operating notes matter for scripts and agents:

- `ensure` and `stop` write bounded progress lines to stderr. Parse JSON from
  stdout only; do not merge the streams before parsing.
- Capacity admission, parking consent and automatic recovery stay inert unless an
  operator enables them. Nothing in this release starts, stops or parks a
  consumer environment on its own.

## Validation

Verify the resolved executable and installed version, then run `devrouter
doctor` and confirm `global.cli-path` reports one authoritative install and no
newer shadow copy. For an authorized managed checkout, run `devrouter status`
and confirm the reported intent, phase, capacity state and attention reason agree
with the runtime you observe. Require each lifecycle operation's own terminal
evidence: a status block or a progress line is not stop or ensure success. When
the gate is wired, prove it once in the harness you use by gating a harmless
command against a settled checkout.

## Report

Report the release revision, the executable and installed version, the
CLI-path diagnostics, the status block for any affected checkout, and the
terminal result of any authorized lifecycle operation. Keep source and package
validation separate from consumer readiness or recovery, and record unknown
ownership or surviving resources as unresolved rather than as recovered.
