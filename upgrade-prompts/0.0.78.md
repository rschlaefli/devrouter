# Upgrade to devrouter 0.0.78

Provider queue diagnostics now distinguish the first waiter from the observed
lock holder. They report held duration and remaining acquisition time, including
that acquisition timeout does not stop the holder. Missing or changing evidence
reports an unknown holder. Acquisition, ownership, cancellation and startup
behavior remain unchanged. No schema, command, flag or environment migration is
needed.

## Task

Use the published 0.0.78 CLI. Update the repository devrouter.version metadata
only when consumer source changes are authorized. Preserve staged work and the
existing runtime owner. Refresh generated agent guidance only with its owner's
authority. No generated runtime configuration or journal rewrite is needed.

For a queued operation, distinguish its queue leader from the observed provider
lock holder. An acquisition timeout describes the waiting operation; it does not
cancel the holder. Unknown holder evidence requires inspection, not lock removal.
Historical configuration-drift repair remains subject to its existing proof gates.

## Validation

Verify the resolved executable and installed version. Use existing captured or
synthetic queue evidence to check holder attribution and timeout semantics; do
not start an unrelated workspace to exercise diagnostics. Require independent
terminal evidence for any already-authorized lifecycle operation. Preserve
live-worker, exact ownership, configuration and surviving-resource checks.

## Report

Report release revision, executable, installed version, queue versus holder
evidence, and terminal operation result where available. Keep source and package
validation separate from consumer readiness or recovery. Record unknowns without
interpreting diagnostic messages as permission to cancel or remove resources.
