# Upgrade to devrouter 0.6.7

Status and doctor keep failed-transition recovery advice consistent, including
combined status insights and unwound-mount diagnostics. Inspect the exact checkout
and resolve the reported transition before retrying ensure; the warning is not
permission to stop/restart an unproved population. Existing readiness, startup,
repair, ownership, levels and literal checkout argument rules remain.
No configuration schema or lifecycle contract changes are introduced.

## Task

Within approved installation/adaptation scope, select the integrity-verified exact
package, update `devrouter.version` in `.devrouter.yml` and refresh existing agent
guidance through `devrouter repo agents`. Verify the actual selected executable,
PATH copies and participating package/source/harness/controller pins. Ask each
participating owner which executable can access this host's Devrouter state;
PATH inventory alone does not prove coordinated adoption.

Before the first 0.6.7 lifecycle write, active participating clients must use a
compatible qualified reader/writer. Older 0.6.6 refuses its newer-writer journals
through direct read, update and global enumeration even without a schema change.
Inactive older pins stay unused until compatible adoption is verified. Unknown
participation holds activation. Do not use an older reader as a downgrade recovery
route after new writes. Preserve all journal bytes, writer stamps and durable
initialization/replacement receipts; never erase state or loosen version/hash
fences to bypass refusal or rearm a consumed attempt.

Installation and release notices supply no consumer startup, repair, replacement,
initialization, reset or extra-attempt authority. Each owner retains exact runtime,
data and neighbour limits. Failed-transition inspection is a diagnostic action;
it does not prove application readiness or prescribe an automatic retry.

## Validation

1. Verify registry integrity, selected package/member bytes, executable version
   and the existing local guidance. Run native checks for actual consumer edits.
2. Use `devrouter status --repo <checkout> --json` and existing diagnostic results
   for authorized inspection. Compare the actual obstruction and next-action
   preconditions before any separately authorized lifecycle command.
3. Any separately authorized runtime work ends with canonical stop and exact
   provider/container/route/worker proof unless the user keeps it running.

## Report

Report exact selected package/executable identities, participating-client adoption,
remaining unknowns and relevant checks. Record any actual runtime terminal with
its producing evidence. Package proof does not establish receiving-host adoption,
consumer recovery, broader guidance parity or retained-maintenance acceptance.
