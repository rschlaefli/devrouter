# Upgrade to devrouter 0.0.79

Managed `ensure` now accepts a devnet upstream alias whose owning container runs
from any Compose project inside the exact worktree. Previously every upstream
alias had to be served by a container started from the checkout's `.devcontainer`
overlay, which rejected repositories that serve a declared upstream from a
workspace-local dependency overlay elsewhere in the same checkout. The workspace
app container still has to come from the managed overlay, and a container owned
by another worktree is still rejected. No schema, command, flag, alias or
environment migration is needed.

## Task

Use the published 0.0.79 CLI. Update the repository devrouter.version metadata
only when consumer source changes are authorized. Preserve staged work and the
existing runtime owner.

Repositories whose upstreams are served by the managed overlay need no change.
Repositories that publish a declared upstream alias from a Compose project
inside the checkout should confirm that project lives under the exact worktree
path used by `ensure`. An alias served from another checkout, a sibling
worktree, or a shared project outside the worktree still fails preflight.

## Validation

Verify the resolved executable and installed version. For an affected
repository, run managed `ensure` and confirm the app container still comes from
the `.devcontainer` overlay while each declared upstream alias resolves to
exactly one running workspace-owned container. Use existing or synthetic runtime
evidence; do not start an unrelated workspace to exercise the change.

## Report

Report release revision, executable, installed version, each upstream alias with
its owning Compose project and working directory, and the app container's overlay
proof. Keep source and package validation separate from consumer readiness, and
do not present an accepted preflight as broader runtime readiness.
