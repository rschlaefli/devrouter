## Product contract

### Commands and lifecycle

| Surface | Required behavior |
| --- | --- |
| `/preview start` | Select a preview alias automatically from the current cumulative merge-base diff and admit the current head revision. |
| `/preview start chat` | Resolve a reviewed repository alias; Klicker's Chat alias selects `chat,ai,mcp`. Allowed alias unions are supported. |
| `/preview extend` / `/preview extend 1h` | Add one hour to the current deadline without rebuilding or changing the deployed revision; default maximum two extensions and four elapsed hours after first readiness, within cost/resource limits. |
| `/preview profiles` / `/preview status` | Show qualified aliases and resolution, or actual revision, state, links, cost estimate and deadline. |
| `/preview stop` | End the disposable preview: fence work, cancel owned pending builds, deactivate compute and delete owned resources/test data. |
| PR/MR close or merge; lease expiry | Request the same teardown automatically. Reopen, push or comment edit never starts an environment. |

Each command is one newly created standalone root comment. Ignore edited/deleted comments, bots, code fences, quotations, ordinary issues and inline review discussions. The parser accepts a small grammar, never arbitrary arguments or shell text. Unknown aliases return choices and no paid allocation. Status replies are rate bounded and do not trigger the bot itself.

Default lifetime: two hours from first readiness, with at most twenty minutes for initial builds, bootstrap and provisioning. Admission arms an independent absolute backstop no later than admission plus two hours and twenty minutes; first readiness tightens it to first-ready time plus two hours. Show the setup cutoff and provisional deadline immediately, then the confirmed expiry when ready. Setup failure or timeout stops work and requests complete cleanup; the two-hour backstop is not permission to keep a failed setup alive. Report serving cutoff separately from verified deletion and residual cleanup cost. Bound queue age independently before spending.

Pushes only mark an existing preview stale. Only a fresh authorized `/preview start [alias]` command may update its revision or profile. Duplicate delivery and a start requesting the already desired revision/profile are idempotent. An update preserves the first-ready time and effective expiry; neither a new revision, alias change nor readiness after an update renews it. Refuse an update when its remaining time cannot accommodate the declared startup budget. Retained pause/resume, automatic wake and activity-based renewal remain outside the initial contract.

The approved one-hour extension command is `/preview extend`, with `/preview extend 1h` equivalent. Add the hour to the last acknowledged persisted expiry, preserving remaining time. Use the same authority and fork rules as start. Reject another extension while an earlier deadline change is unresolved; distinct comment IDs request distinct increments, including comments from different authorized people. Accept only a fresh authorized command for an unexpired session that has reached initial readiness; never revive an expired, stopping or closed change. Duplicate delivery adds time once, while a genuinely new command requests another increment. Recheck remaining installation/repository lifetime and cost allowances. The approved default allows two successful one-hour extensions per session and at most four elapsed hours after first readiness. Reviewed installation policy may configure a different bounded ceiling; repository policy cannot exceed it. The product default does not extend the existing pilot or grant new spending. Extension changes no source, profile, application data or build. Acknowledge the new absolute expiry only after durable state, provider expiry and independent cleanup agree within the qualified clock/rounding bound. Refuse if cleanup has begun or the provider-qualified safety window cannot accommodate the change; a refresh still loses to the deadline. An unsupported or uncertain extension reports its state and cannot promise the additional hour.

Automatic selection binds to the admitted head SHA, fetched target SHA, computed merge-base and trusted manifest/policy digests. Read the complete name/status diff, including both sides of renames/deletions, with explicit API pagination/truncation detection or a bounded local Git metadata diff that executes no candidate code. Documentation-only changes return a no-runtime result. Collect all matching rules and union their allowed aliases; shared-surface rules may declare a dominating `full` alias. Every union is validated against the trusted allowed combinations and provider capabilities. Unmatched executable paths use an explicitly configured conservative fallback, normally `full`; without one return selection-required, not an empty or cheapest profile. Changes to control/config files return review-required. Unavailable merge-base, exceeded bounds or incomplete diff return unknown and refuse automatic start; a manual allowed alias may proceed only if source identity/control-file compatibility is independently complete. Unknown alias, unsupported member or denied union fails before effects. Record reasons and omitted coverage in the plan.

The logical identity is forge host + immutable project/repository ID + PR/MR number. A fresh start after deletion receives a new generation and unique provider resources/URLs. Keep links stable within a generation and the bot comment stable across generations. A newer start waits for predecessor cleanup; stale commands, timers and build completions cannot mutate a later generation. Local `devrouter stop` remains reversible. Remote `preview stop` explicitly ends a disposable preview and announces data deletion; the command namespace and help distinguish the two meanings.

One bot-owned status comment reports queued/building/initializing/ready/stopping/stopped/expired/failed/cleanup-pending. Track the exact bot comment ID and verify its author before updates. Publish app links only after declared readiness and behavior checks; show which SHA is deployed and when the source has moved. Mark stopped/expired only after absence is proven. A failed cleanup holds its reservation and says cleanup pending. Never use the comment as durable state or expose signed login links, credentials or private logs.

## Architecture and packaging decisions

### One product, isolated remote subsystem

Keep the existing repository, npm package, pnpm lockfile and thin CLI-command pattern. Add `src/commands/preview.ts` delegating to an isolated `src/core/preview/` subtree. Register the command lazily in `src/cli.ts`. Use ordinary internal interfaces and a static built-in provider registry. Do not introduce a pnpm monorepo, extra npm packages, dynamic third-party plugin loading or a permanent controller service for the initial release.

Proposed CLI responsibilities are `preview init`, `plan`, `stop`, `status`, `handle-event`, `sweep` and `doctor`. `plan --list` supplies the alias inventory and `/preview profiles` response. Starting goes through the authenticated forge command/manual-CI path, rather than a second unauthenticated CLI admission path. Operator status/stop use the same engine with an explicitly configured operator identity/policy; no caller can supply an arbitrary actor ID. `init` renders an onboarding diff and setup checklist; it is non-mutating by default and writes explicitly chosen local files only with a named write option. It never creates cloud resources, forge apps, secrets or workflow permissions automatically. `plan`, help and local commands require neither cloud credentials nor a running local router/Docker daemon. `doctor` distinguishes static checks from an explicit values-free live probe.

The engine owns intent, policy, selection, admission and reconciliation. Providers own remote resource effects. Forge adapters own current identity/authorization/comment lookup and status publication. A state adapter owns conditional durable storage. Repository recipes own application build and initialization semantics. Each reports structured versioned results and explicit unsupported capabilities. Success is independently observed, not inferred from a mutation returning HTTP 200.

### Configuration: separate remote contract and two trust levels

Add a versioned opt-in `.devrouter.preview.yml`, read exclusively by preview commands, alongside the existing `.devrouter.yml`. It is a remote deployment contract analogous to the existing repository-owned profile-plan document. Reuse the current bounded regular-file/realpath/symlink guards and strict unknown-field validation. Local commands never load this manifest, so preview-only edits cannot invalidate raw `.devrouter.yml` fingerprints and older local CLIs continue to work. Do not add remote domains to `apps[].host`, relax `.localhost` validation or change local runtime identity. The implementation ADR and AGENTS wording must explicitly approve and document this scoped configuration exception.

The preview manifest contains alias-to-profile references, changed-path rules, resource/build/image bindings, ports, initialization/migration jobs, synthetic fixture ownership, readiness and non-secret runtime bindings. Existing Devrouter adopters select the current profile closure and map selected logical app/service/process names to cloud resources. Keep membership in profiles, not a parallel cloud list. Model deployment ordering and required backing-resource edges once in the cloud graph. A profile process marker such as `klicker-dev` is not automatically a deployed worker; mappings explicitly identify deployable processes.

A cloud-only adopter may use a minimal `.devrouter.yml` with `apps: []` and resource-based aliases in the preview manifest; it need not adopt local routing. It needs no fake localhost routes, DevPod, pnpm application stack or devcontainer. Profile-backed and resource-backed selectors produce the same normalized resource graph. The graph is a small bounded resource DAG, not a new CI language or a generic templating engine. Container recipes and finite jobs run application commands only inside isolated builders/workloads; the privileged controller never runs event-supplied application scripts.

Trusted installation policy is loaded from a reviewed controller revision plus runtime bindings: authorized roles, allowed aliases/provider projects, domains/viewer policy, TTL/build/time/count/cost ceilings, state namespace and secret-source/recipient allowlists. Candidate configuration cannot broaden these. Configuration digests bind admission to the reviewed graph; changed control files block until reviewed configuration delivery. Resource names, app origins and synthetic test URLs use scoped bindings instead of string replacing arbitrary templates. Secret values never enter plans, fingerprints, comments, template arguments/run history or build arguments.

Use native `DEVROUTER_PREVIEW_*` environment injection and explicitly scoped provider/state/source variables. Our installations obtain them from Infisical, but the public CLI does not require our operator binary or embed an Infisical project. Source-clone, bot-write, provider-control and application-runtime credentials have different scopes and lifetimes. A candidate build or workload cannot access the controller credentials.

### Provider contract and Northflank implementation

Northflank and state REST transports may use built-in `fetch`, with adapter-local authentication. Prefer workflow-supplied short-lived OIDC-derived credentials where available; native scoped environment credentials remain an explicitly configured option. Do not hand-roll JWT/OIDC validation or reject a justified first-party SDK solely to claim zero dependencies. Any new dependency is introduced only when a concrete auth/API requirement warrants it, pinned and lazy from the preview path. No cloud SDK or auth work may enter local CLI startup.

The provider interface advertises support and limits for container services, database/cache addons, volumes, finite jobs, secret references, ingress/access, hard expiry and observation. Required lifecycle operations are plan/estimate, create or reconcile a stage, observe readiness/absence, cancel owned work and destroy exact owned resources. Deadline adjustment is an explicit capability; a provider lacking qualified extension behavior rejects that command before effects. Core state and user commands contain no Northflank project/plan/blueprint shape. Unsupported resources fail before reservation/provisioning; do not emulate unsupported behavior silently.

Northflank is the first bundled live adapter. Keep its templates, object IDs, allocation sizes, API calls and secret-delivery rules inside `src/core/preview/providers/northflank.ts` and adapter-owned resources. Use existing native Blueprints where they provide ownership/lifecycle value, without an additional generalized workflow engine. Provider-specific configuration is a namespaced overlay, not fields sprinkled through the core graph.

Create initially inactive compute, establish owned data/storage, attach narrowly scoped runtime secrets, run declared fresh bootstrap/migrations/seed-on-create, deliver generated runtime credentials through secret channels, then start selected services in dependency order. Reconcile the exact immutable source/image and public origins before enabling ingress. A successful TCP probe is not adequate application acceptance. Updates never reseed retained data. A fixture/bootstrap incompatibility returns an explicit recreate requirement rather than destroying data as part of update.

Hatchet, Prisma, Redis roles and Klicker cookie rules belong in Klicker's recipes and acceptance checks. A plain HTTP application uses the same engine without them. A devcontainer/Compose manifest can inform onboarding, but does not prove images, cloud data ownership or secret/access policies are deployable. Preserve backend image reuse by immutable build/config identity; frontend bundles that embed preview URLs require per-environment builds until runtime configuration is qualified.

Persist deterministic provider names and effect intent before each allocation. After uncertainty, inspect exact IDs/UIDs instead of blind retries. A janitor requires durable pre-write intent or receipt plus matching installation, generation and immutable provider identity. Tags alone, a missing state file or an age guess never authorize adoption/deletion; ambiguous resources are quarantined and reported. Cleanup includes partial bootstrap jobs, addons, volumes, secrets, route claims, provider preview metadata and abandoned builds. Never take ownership of the manually created Klicker pilot. Provisioning readiness, source compatibility, actual deletion and metered cost are distinct receipts.

### State, admission and deadlines

Use a private versioned remote state backend with conditional writes. Azure Blob is the initial deployment candidate, behind a small backend interface; memory is for deterministic tests and read-only file snapshots are for plans, not live CI mutation. Qualify compare-and-swap, authentication, expiry/retention and availability before enabling effects. Provider and state credentials remain in the installed platform secret scope, not per-PR configuration.

Persist normalized command identity, logical preview/generation, approved policy/config/source, desired resources, initial setup cutoff, first-ready time, confirmed expiry, deadline revision, operation cursor, immutable ownership receipts and reservations. Use per-preview conditional writes plus a pool-wide admission record with crash reconciliation. Reserving capacity/cost precedes provisioning; release only after verified absence. An interrupted cross-record operation may over-reserve temporarily but cannot undercount live or unknown effects. Cross-project budgets require a deliberately shared pool; otherwise each installation stays project-scoped.

For GitHub, the forge's persisted comment history is the initial recoverable inbox: receipt by Actions alone is not durable ingestion. A handler re-fetches the command and writes an authorized intent before provider work. The installation sweep independently polls configured project/change comment histories, so a missing/cancelled workflow does not require another user comment. GitLab uses the same recovery path even if a Note Hook receiver exists. Only registered installation projects are polled; no account-wide discovery. The project list is explicit remote installation policy, not a machine-global local-workspace registry.

Maintain per-change processed IDs, a replay watermark and a completed-scan boundary. Read pages through a fixed upper boundary from the forge API with overlap and deduplication. Persist each validated intent before its processed marker, and advance the completed boundary only after every required page is obtained and accounted for. Missing pages, truncated history or lookup failures keep the old boundary and refuse recovery-driven starts. Comments qualify only if current API content proves they are original unedited root human commands, within the short configured admission-age window, with current actor authority. Deleted/unreadable comments not already admitted cannot create an intent; deletion never cancels an admitted intent. Long polling gaps may intentionally expire a start command and report that a fresh command is needed, rather than spending late.

Before admitting a recovered start, establish complete relevant command history through that boundary and the current change state. Process control commands in a forge-qualified stable creation order and evaluate terminal stop/close/expiry fences before producing earlier start effects; do not create then immediately delete for an already superseded start. Current closed/merged state dominates commands; reopens require a newer explicit start. Replayed starts cannot reset a TTL. Native CI queuing is a delivery optimization, not the state machine.

Within a generation, every new admitted desired revision receives an increasing operation version and source/config digest. Conditional state writes claim a short execution lease for each mutation stage. A worker revalidates generation, operation version, deadline and lease immediately before each provider write and before status publication. A changed operation invalidates the old worker; provider calls already in flight remain recorded outstanding effects, not cancelled by a local fence. Stop advances the operation fence, denies new writes and cancels/deactivates exact owned work. It must remain actionable while builds are pending; no workflow lock spans an entire expensive build.

Same-generation updates also have a provider-write ordering barrier: a newer desired operation may be recorded/coalesced immediately, but cannot mutate shared resources until every superseded mutation touching them is terminal or the provider enforces an equivalent immutable revision fence. V1 uses terminalization and read-back rather than assuming a provider fence. Superseded builds may finish as inert artifacts, but cannot deploy. If update A was already accepted remotely, update B waits for A to finish/cancel conclusively and reconciles its actual result before issuing B. B publishes ready only after observing the admitted image/source and non-secret configuration identity. Thus late A cannot overwrite a ready B. A stalled or unknown mutation blocks B's mutations/readiness, keeps its reservation and eventually enters cleanup under the current confirmed deadline; it does not block the independent stop/cancel path.

Each submitted provider operation retains its idempotency/request identity and terminal status. Teardown first waits for or conclusively cancels every outstanding create/update/build request, then observes and removes any resulting exact-owned allocations, and only then verifies absence and releases reservations or admits a successor. A one-time absence observation cannot prove a still-pending create will not appear later. A late accepted resource remains charged and must be caught by receipt-based reconciliation and the provider-side janitor. An ambiguous pending request keeps cleanup-pending and blocks identity reuse; it is never forgotten on timeout. Provider conformance must prove the terminal-operation/absence boundary used for its receipts.

Every live generation needs an independent provider-side deadline backstop armed before paid resources. Qualify native expiry against the initial backstop, first-ready tightening and explicit extension, across all resource classes including failed pre-blueprint allocations. Disable expiry reset on ordinary preview updates. Northflank documents a separate reset endpoint accepting a lifetime in minutes and returning expiryTime; this is a candidate for deadline adjustment, not proof of exact absolute-deadline or retry semantics. Pin the intended absolute target before effects, derive bounded remaining lifetime and verify returned/read-back expiry. Retries cannot recompute another full increment. Version deadline changes separately from source updates, fence stale cleanup timers against current state, and let stop/close/expiry teardown win over a pending extension. Qualify integer-minute rounding, clock tolerance, partial failure and a cleanup worker already acting on the old deadline before declaring extension supported. If native expiry is incomplete, require a provider-native janitor over persisted ownership before creation. A periodic installation/pool sweep complements native expiry and runs independently of PR activity; opportunistic sweep follows any control run. Avoid a five-minute Actions cron in every adopting repository. CI timing alone cannot promise a strict spend cutoff; report cleanup latency and reserve its allowance.

Billing alerts notify, and allocation estimates/reservations constrain planned cost. Neither is a guaranteed invoice cap. Include provision/build timeouts, attempt caps, concurrency and optional model allowances. At deadline or stop, deny new work, stop compute promptly and verify complete deletion with bounded retries/backoff and an actionable failure state. Credential expiry must leave the independent cleanup mechanism able to finish.

### Forge adapters and easy adoption

Use one team-operated installation for provider/state/cleanup, with explicit repository resource, credential, access and quota boundaries. Onboard each repository through a manifest and a small pinned CI wrapper. A dedicated installation remains available for projects needing stronger separation. Share controller code and administration without sharing candidate-runtime access across repositories.

GitHub uses a tiny consumer default-branch wrapper for `issue_comment.created`, close events and manual inputs, calling a Devrouter-owned reusable workflow pinned to an immutable revision. The reusable workflow installs the exact CLI artifact and invokes the common handler. `preview init` renders the small caller; no additional composite action is needed in v1. Add a standalone action later only when a second concrete composition needs it. Show explicit input/secret mappings and least required permissions. No `secrets: inherit`, candidate checkout execution, floating tool versions or broad application installs in a privileged job. Public/private callers must pass organization Actions policy checks. Self-hosted runners declare Node/tool/network prerequisites.

GitLab uses the same CLI and a namespaced pinned template with validated inputs. Prefer same-instance `include:project` or a CI component when available. Public immutable `include:remote` plus integrity or reviewed vendoring supports a GitHub-hosted upstream; private includes and components cannot assume cross-instance access. Self-hosted installations may mirror/vend the small wrapper while using the same exact CLI artifact. No GitLab mirror/catalog or new remote is created automatically. `include:remote` is public and does not support authentication; older GitLab instances without integrity use a reviewed vendored template. A future same-instance component/mirror is an installation option, not a dependency for generic adoption.

GitLab MR comments arrive as Note Hook events. The current official direct webhook-to-trigger example documents Push/Tag, so direct Note Hook-to-trusted-pipeline is a bounded qualification item. If unsuitable, ship a minimal serverless ingress adapter that verifies the configured hook secret/project/delivery identity and requests a pinned trusted pipeline. The receiver holds no deployment token and executes no candidate code. Manual CI input is a useful fallback but does not satisfy live comment parity. Avoid making an always-on shared app a prerequisite for GitHub; reusable ingress later can reduce multi-project setup.

Both adapters re-fetch the immutable project ID, comment, actor's current write/maintain capability, open PR/MR state and current source SHA. Author-association strings are insufficient. V1 accepts trusted same-repository branches; forks are denied even when an authorized maintainer posts the command. Every preview requires the installation’s approved viewer access policy, regardless of source-repository visibility. Network-restricted installations must prove that an outside source is denied before reporting ready; application login alone does not prove network enforcement. Anonymous real-AI previews are rejected unless a separately approved bounded upstream/viewer policy exists; mocked AI must be labelled as such. Controller and candidate source/build trust remain separate.

The user selected UZH network restrictions for the Klicker installation, following the existing ingress-protection approach. Configure the approved source networks once in trusted installation/repository policy and apply them automatically to every preview, including demos. Use the provider’s native ingress IP/CIDR controls. No shared viewer password, extra access gateway or mandatory SSO is required. Application authentication and authorization remain separate requirements.

Keep the reusable Devrouter contract provider-neutral: a network allowlist is an installation policy, not a UZH-specific core default. Obtain exact networks from the existing approved ingress policy during authorized activation; keep operational ranges in private installation configuration. Candidate code/configuration cannot widen them. The provider adapter must qualify trusted client-source evaluation, IPv4/IPv6 behavior and consistent protection across every custom and provider-generated URL and exposed app/API port before enabling ingress. Backing databases and workers stay private. Readiness probes must use private connectivity or an explicitly approved source, without a public bypass. Test access from an allowed source and denial from outside the configured networks; a source-repository permission or application login is insufficient. Unsupported or uncertain enforcement fails closed and prevents ready publication.

Onboarding output is a small config diff plus wrapper files, secret/role names and validation steps. Reuse a configured domain wildcard, with a short repository/generation label, instead of manual DNS per preview. Application-origin/cookie compatibility is an onboarding requirement. `preview init` and `doctor` show which support cell is qualified, mocked or unavailable; the CLI must not advertise a project as ready after only generating YAML.

## Research, decisions and boundaries

Current primary evidence confirms GitHub reusable workflows can serve public/private callers under configured access policy, `issue_comment` executes from the default branch, and concurrency queues can be enlarged but are not a durable delivery log. GitLab components are same-instance; public remote YAML supports integrity and private remote includes do not authenticate. Northflank provides expiry with optional reset-on-update plus a separate expiry-reset API; run concurrency does not cap existing previews. Native ingress supports IP and password rules; organization SSO has additional organization/directory prerequisites and appears in Enterprise pricing. Do not make paid SSO a baseline requirement. The platform's hosted request-triggered whole-stack wake remains unqualified and is outside v1.

Decision-changing proofs before live activation: fresh native provisioning with private credential delivery; complete hard-deadline cleanup after partial failure; state/admission crash recovery; GitLab Note transport; private app denial; application origin compatibility. Resolve these in synthetic fixture tests and separately scoped live trials before support claims. A missing optional integration must report a capability gap rather than falling back to broader credentials.

Alternatives: keep the feature only in Klicker (rejected by user); separate companion product/monorepo/plugin marketplace (deferred as unnecessary); add another cloud driver now (deferred until a real consumer asks); always-on orchestration server (deferred, CI/native jobs suffice); auto-translate devcontainers or arbitrary Compose to cloud (deferred, recipes remain explicit); HTTP wake/idle tracking (deferred; fixed disposable lease is predictable).

Store opaque actor/project/comment identifiers only when necessary for authorization and replay; do not copy names, emails, raw comments/webhook bodies, real application data or credentials. Use synthetic fixtures. Keep operational records private and purge identity details after verified teardown plus the configured bounded recovery window; keep only a minimal replay watermark while still needed. Installation owners choose audit retention/basis before activation. Status text makes the lifetime and deletion effect explicit. This is an engineering design measure, not a legal-compliance certification.
