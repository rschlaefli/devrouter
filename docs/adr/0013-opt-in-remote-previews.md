# ADR 0013: Remote previews are an opt-in Devrouter capability

Status: Accepted. Offline manifest/profile planning is implemented; lifecycle, provider and forge packages remain pending.

Devrouter will package remote review environments, reusable forge integrations and deployment-provider adapters as one product, with Northflank as the first provider. Keeping the feature only in application repositories would duplicate lifecycle and integration work across projects; provider and forge adapters let projects retain their own build and initialization recipes while sharing control behavior.

The boundary preserves the side-effect-free profile contract in [ADR 0007](0007-keep-ci-profile-planning-repository-owned.md) and the local idle-stop ownership in [ADR 0012](0012-devrouter-owns-idle-stop.md). Use a separate opt-in `.devrouter.preview.yml` manifest. The user accepted this exception when justified: the current local controller fingerprints raw local-config bytes, and older local parsers reject unknown root keys. Putting remote-only settings into `.devrouter.yml` would disturb local sessions and compatibility. Local runtime/profile configuration remains in `.devrouter.yml`; preview aliases reference its profile membership. This is a scoped successor to ADR 0007: Devrouter interprets a closed remote resource vocabulary only through `.devrouter.preview.yml`; offline planning executes no application commands. Local profile-plan bindings retain their original literal-only contract.

Remote state, credentials, domains and expiry remain independent of local routing and workspace ownership. A shared team-operated installation isolates each repository’s resources, access, credentials and quotas. Disposable remote stop deletes owned test resources; the local reversible Stop term retains its meaning. Routine timing, explicit source-update and extension behavior belong in the [implementation plan](../project/2026-10-25-cloud-preview-environments-plan.md), rather than duplicating that contract here.

GitHub with Northflank is the first beta; genuine GitLab and a second application stack are required before general availability claims. The Klicker installation uses UZH network restrictions through the provider’s native ingress controls; reusable policy remains a generic network allowlist supplied per installation/repository. This supersedes the proposed shared-password access gateway. Exact network ranges and enforcement proof belong to authorized activation. The product interview also settled the lifecycle defaults recorded in the implementation plan. These design choices grant no implementation, activation, publication or new paid-resource authority.
